Two-layer design:
- Scheduling layer (`scheduler.py` + `jobs.py`): a single process invoked every 5 minutes by one crontab entry; `JOBS` is the authoritative dict of `{freq, script, args, env, timeout, offset_min}` entries grouped into 5m/15m/30m/1h/6h/1d/1w/1m tiers with minute offsets for staggering. `_is_due` implements all frequency semantics (including dow/dom) and `main()` optionally acquires an OS-level flock (`cron/_flock`) to prevent overlapping runs.
- Execution layer: each job is launched as a subprocess via `subprocess.run(..., timeout=job['timeout'])`. Long-running work is never run inline — most jobs invoke `enqueue_task.py --task-type <type>` which inserts a row into `task_queue` via `background.background_queue.enqueue_task`, letting the persistent `background_worker.py` daemon do the actual work under its own locking and retry policy. Direct-script jobs (e.g. `background_worker --drain`) are the exception and must be short-lived.
- Persistence layer (`cron_runs.py`): lightweight SQLite helper over the `cron_runs` table recording start/complete/error/output per scheduler tick, consumed by `_write_status` → `memory/.cron_status.json` and the MCP health tool.
- Observability helpers: `manage_task_timeouts.py` reads/writes the `cron_task_timeouts` table (per-task-type `timeout_s`, `max_attempts`, auto-retry knobs); `monitor_task_queue.py` is a read-only watchdog that warns on excessive pending depth or stale task types.
Dependency direction: `scheduler.py` → `jobs.py` → `enqueue_task.py` / direct scripts; both `scheduler.py` and `monitor_task_queue.py` depend on `infra.db_write_queue` and `background.background_queue`; `cron_runs.py` depends only on `sqlite3` and `infra.memory_common.GLOBAL_MEM_DIR`.
