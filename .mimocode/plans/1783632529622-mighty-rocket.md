# Plan: Cron Consolidation + System Health Dashboard

## Problem Statement

39 crontab entries, each spawning a Python process with its own flock, logging, and failure mode. The `*/15 min` background worker was already reduced from `*/5` due to runaway workers. Every cron is a potential source of silent failures. Health checks are scattered across `cron_health_check.py`, `memory_health_check` MCP tool, `dashboard.py`, and log files. There is no centralized "is the system healthy?" answer.

## Current State

| Metric | Value |
|--------|-------|
| Crontab entries | 39 |
| Phase B (enqueue_task.py) | 31 |
| Direct-run crons | 8 (health_check, watchdog, daemon_watchdog, config_drift, policy_hash, background_worker, + 2 watchdog variants) |
| Cron execution tracking | **None** — no `cron_runs` table, log files are ephemeral |
| Health check surfaces | 3 (cron_health_check.py, memory_health_check MCP, dashboard.py) |
| Failure reporting | Per-log-file only, no aggregation |

## Architecture: Two-Component Fix

### Component 1: Consolidated Cron Scheduler

Replace 39 crontab entries with **1 crontab entry** that runs a scheduler. The scheduler groups jobs by frequency and executes them in batches with shared flock, centralized logging, and execution tracking.

**New file: `cron/scheduler.py`**

The scheduler is a simple script (not a daemon) invoked by a single crontab entry every 5 minutes. It:
1. Reads a job registry (YAML/dict) that defines all jobs with their frequency, function, and config
2. Determines which jobs are due based on current time + frequency
3. Runs due jobs sequentially within each frequency tier
4. Records execution to a new `cron_runs` table
5. Writes a consolidated `memory/.cron_status.json` (analogous to `.health_status.json`)

**Frequency tiers** (reduces process count from 39 to ~8 invocations/hour):

| Tier | Cadence | Jobs | Process count |
|------|---------|------|---------------|
| **Immediate** | Every 5 min | background_worker, health_check, daemon_watchdog, task_queue_monitor | 12/hr |
| **Hourly** | Once/hour at :05 | sync, crdt_sync, policy_hash_status | 1/hr |
| **Daily** | Once/day at 01:00 | digest, purge_auto_saves, cleanup_auto_logs, backfill, backup, backup_validate, heartbeat, kg_backfill_monitor, embedding_recompute, detect_vec_drift, config_drift, auto_share | 1/day |
| **Weekly** | Once/week (Sun) | integrity_check, log_retention, tier_migration, kg_backfill, consolidate, rewrite_links, pinned_decay, concept_drift, semantic_clusters, skill_decay | 1/week |
| **Monthly** | Once/month (1st) | compact, purge_expired | 1/month |
| **On-demand** | Enqueued by daily/weekly | skill_extraction, cross_session_learn, quality_filter, auto_summarize, retention_stats, promote_drafts | via worker |

**New crontab** (replaces all 39 entries):

```bash
# Single entry: run scheduler every 5 minutes
*/5 * * * *  MEMORY_DB_PATH=... venv/bin/python cron/scheduler.py >> memory/scheduler.log 2>&1
```

**`cron_runs` table** (new migration 037):

```sql
CREATE TABLE IF NOT EXISTS cron_runs (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    job_name    TEXT NOT NULL,
    started_at  TEXT NOT NULL DEFAULT (datetime('now')),
    completed_at TEXT,
    status      TEXT NOT NULL DEFAULT 'running',  -- running|completed|failed|skipped
    duration_ms INTEGER,
    error       TEXT,
    output      TEXT  -- last 500 chars of stdout/stderr
);
CREATE INDEX IF NOT EXISTS idx_cron_runs_job ON cron_runs(job_name, started_at DESC);
CREATE INDEX IF NOT EXISTS idx_cron_runs_started ON cron_runs(started_at DESC);
```

**Migration**: `migrations/037_cron_runs.sql` + `migrations/037_cron_runs.down.sql`

**Key design decisions** (confirmed with user):
- Scheduler is a **script, not a daemon** — simpler, no long-lived process management, cron handles restart
- Jobs run **sequentially** within tiers — no new threading/lock complexity
- Existing cron_*.py scripts are **unchanged** — scheduler calls them as **subprocesses** (no import side effects, no code changes to existing scripts)
- `install_crontab.sh` is updated to emit 1 entry instead of 39
- Old crontab block is replaced atomically (existing idempotent pattern)

### Component 2: Comprehensive System Health MCP Tool

Replace the scattered health checks with a single `memory_system_health` MCP tool that returns green/yellow/red with actionable next steps.

**New file: `mcp_health.py`** (or extend `mcp_maintenance.py`)

The tool consolidates 6 health dimensions into one response:

```python
@mcp.tool()
def memory_system_health() -> str:
    """Comprehensive system health: green/yellow/red with actionable next steps.
    
    Returns a JSON dict with:
    - overall: "healthy" | "degraded" | "critical"
    - subsystems: {name: {status, details, action}}
    - recent_crons: last 24h execution summary
    - action_required: list of strings with next steps
    """
```

**6 health dimensions**:

| Dimension | Source | Green | Yellow | Red |
|-----------|--------|-------|--------|-----|
| **Database** | `memory_health_check` existing | accessible, no drift | vec drift > 0 | inaccessible |
| **Search** | `cron_health_check` semantic_search probe | returns results | slow (>500ms) | fails |
| **Background Worker** | `cron_runs` table | last run < 15min ago | last run 15-60min ago | last run > 60min ago or failed |
| **Cron Jobs** | `cron_runs` table | all jobs completed in last 24h | some failed | >3 jobs failed in 24h |
| **Auto-Save** | `background.auto_save.health_check()` | circuit closed, recent saves | circuit open < 5min | circuit open > 5min |
| **Disk** | `shutil.disk_usage()` | < 80% used | 80-95% used | > 95% used |

**Response shape**:

**Registration**: Add `memory_system_health` as a **new CORE tool** alongside the existing `memory_health_check`. The existing tool stays for backward compat. Add to `tool_registry.py` and wire through `memory_mcp.py`.

## Migration Strategy

1. **Phase 1**: Add `cron_runs` table (migration 037) + `cron/cron_runs.py` helpers
2. **Phase 2**: Build `cron/scheduler.py` + `cron/jobs.py` — run in parallel with existing crontab (dry-run mode)
3. **Phase 3**: Build `mcp_health.py` — new MCP tool, no impact on existing tools
4. **Phase 4**: Update `install_crontab.sh` to emit 1 entry — old entries replaced atomically
5. **Phase 5**: Update AGENTS.md, tests, docs

Each phase is independently shippable and testable.

## Risk Assessment

| Risk | Mitigation |
|------|-----------|
| Scheduler script fails to start | Fallback: old crontab entries can be restored from git |
| Job registry misses a job | Comprehensive audit of all 39 entries during Phase 2 |
| cron_runs table grows unbounded | Add `cleanup_old_cron_runs` to daily maintenance (keep 30 days) |
| Health tool adds latency to MCP calls | Tool is on-demand only (not called per-session), no caching needed |
| Breaking existing cron_*.py scripts | Scheduler calls them as subprocesses — no code changes to existing scripts |
