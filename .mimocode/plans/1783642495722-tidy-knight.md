# Plan: Production-Grade Fixes for Agentic Memory Resource Exhaustion

## Problem Summary

Three interrelated failures causing the agentic memory system to degrade:

1. **Compaction-save directories accumulate indefinitely** (4.3GB, 30 dirs) — `_enforce_compaction_pin_limit()` cleans `.md` files and DB rows but never deletes the actual `compaction-save-*/` directories containing `events.jsonl`
2. **Duplicate MCP server processes** — no singleton guard in `memory_mcp.py`, so two instances compete for the same DB flock, causing cascading lock contention
3. **Circuit breaker trips 1,290 times** — flock contention from (2) causes precompact-snapshot hooks to fail, which trips the auto-save circuit breaker in rapid open/recover cycles

---

## Fix 1: Clean Up Surfaced Compaction-Save Directories

**File:** `context_monitor.py` — `_enforce_compaction_pin_limit()` (lines 1083–1156)

**What:** Extend the existing retention function to also delete `compaction-save-*/` directories older than `COMPACTION_RETENTION_DAYS` (3 days). Currently it only cleans `.md` files and DB rows.

**How:**
- After deleting old `.md` files (line 1128), iterate `sessions_dir.glob("compaction-save-*/")` and delete directories whose timestamp parses to older than `COMPACTION_RETENTION_DAYS`
- Use the same `_compaction_note_age_days()` helper (adapted for directory names like `compaction-save-20260704T193402`)
- Skip directories that contain unsurfaced `.task.md` (conservatively — only delete if `.surfaced` marker exists OR age > 7 days)
- Log the count and total size freed

**Why this is durable:** `_enforce_compaction_pin_limit()` is called from two places:
1. `context_monitor.py:pre_compaction()` — every compaction event
2. `infra/pinned_decay.py` — weekly cron job

Both paths will now clean up directories. The 7-day hard cutoff for unsurfaced dirs prevents orphan accumulation even if surfacing fails.

## Fix 2: Singleton Guard for MCP Server Process

**File:** `memory_mcp.py` — add startup guard before MCP server starts

**What:** Prevent multiple `memory_mcp` processes from running against the same DB. This is the root cause of flock contention.

**How:**
- Create `infra/mcp_singleton.py` with a PID-file-based singleton guard:
  - Lock file: `<memory_dir>/.mcp_server.pid`
  - On startup: read existing PID, check if process is alive via `os.kill(pid, 0)`
  - If alive: log warning and exit (or adopt — see below)
  - If dead/stale: overwrite with current PID
  - On shutdown: remove PID file (via `atexit` + signal handlers)
- In `memory_mcp.py`, call the guard before `mcp.run()` or equivalent server start
- Use `fcntl.flock` on the PID file for atomicity (same pattern as `inbox.py` daemon)

**Adopt-or-reject behavior:**
- If an existing MCP process is detected, the new process should **not** start — it should log a clear error and exit with code 1
- This matches the daemon pattern in `inbox.py` (lines 429–456) where `is_daemon_running()` checks the flock

**Why this is durable:** The PID file + flock pattern is already proven in `inbox.py` for the daemon. Applying the same pattern to the MCP server prevents the duplication at the source.

## Fix 3: Improve Circuit Breaker Recovery

**File:** `background/circuit_breaker.py`

**What:** Make the circuit breaker more resilient to transient flock contention.

**How:**
- In `_auto_save_record_failure_and_maybe_trip()`, distinguish flock-contention failures from real save failures:
  - Flock contention = `FileLockError` or timeout acquiring lock → don't count toward circuit breaker threshold
  - Real failures (DB corruption, disk full, etc.) → count toward threshold
- Add a `_is_flock_contention(error)` helper that checks error type/message
- When flock contention is detected, log at `debug` level instead of `error`, and skip the failure count increment

**Why this is durable:** Flock contention is expected during high concurrency (two MCP processes, cron jobs overlapping). Treating it as a real failure causes unnecessary circuit-breaker trips that cascade into auto-save failures.

## Fix 4: Clean Up Stale Lock Files on Startup

**File:** `infra/db_path_flock.py`

**What:** Detect and clean stale flock files left by crashed processes.

**How:**
- In `_ensure_fd()` (line 138), after opening the lock file, check if the existing flock is held by a dead process:
  - Try non-blocking acquire
  - If it fails, check if the holding PID is alive
  - If dead: close fd, reopen, and acquire (effectively stealing the stale lock)
- This mirrors the stale-sentinel detection already in `circuit_breaker.py:_is_stale_sentinel()` (lines 94–117)

**Why this is durable:** Prevents the scenario where a crashed process leaves a stale flock that blocks all subsequent writes indefinitely.
