# Performance Benchmarks

## Goal

Understand the expected performance characteristics of the agentic-memory system — search latency, write throughput, index rebuild times, and memory footprint — to plan capacity and diagnose slowdowns.

> **These numbers are real measurements**, produced by running the benchmark suites in this repo (`eval/benchmarks/bench_save.py`, `eval/benchmarks/bench_search.py`, `eval/perf_envelope.py`) on the date shown below. They **replace the earlier placeholder tables**, which were aspirational and off by 1–2 orders of magnitude (e.g. the old "12 ms save" is actually 46 ms–3+ s depending on corpus size and whether LLM fact extraction is enabled).

## How these were produced (methodology)

- **Date run:** 2026-07-10
- **Hardware:** Apple M5 Pro (15 cores), 24 GB RAM, macOS 26.5.2
- **Runtime:** Python 3.14.6 in the project venv (`venv/`), all extras installed
- **Corpus:** synthetic notes generated by the benchmark scripts (valid frontmatter + body). Each corpus is built from scratch into a temporary SQLite DB.
- **Warm vs cold:** the DB is freshly built for each corpus size (cold cache); each measured operation is warmed up (2 iterations) before the timed iterations, so the reported numbers reflect steady-state, not first-call model loads.
- **Percentiles:** p50 / p95 / p99 / max / mean over all recorded operations for that corpus size (save = every note written; search = 5 representative queries × each mode).
- **Environment flags used to get reproducible core-path numbers:**
  - `MEMORY_USE_USEARCH=0` — skip the usearch vector-index warm-up (one-time 2–4 s) that is irrelevant to latency percentiles.
  - `MEMORY_LLM_EXTRACTION=0` — disable the LLM fact extractor (Qwen2.5-3B) so we measure the **deterministic core write/search path** (FTS5 + file writes + vector-key bookkeeping) rather than per-note LLM cost. The default config has LLM extraction **on**; see the note under *Write path* for how much it adds.
  - `PYTEST_CURRENT_TEST=1` — disables config-drift enforcement, which otherwise **hard-blocks `save_memory`** whenever a feature flag set in the environment diverges from `memory.toml` (a source-conflict). This is the same short-circuit the repo's own test suite relies on. Without it, the benchmark cannot write a single note when any flag is overridden.

> **Important:** the scripts measure the live `save_memory` / `search_memories` code paths end to end (saga transaction, FTS5 incremental index, atomic file write, drift check). They are the source of truth for these numbers; do not hand-edit the tables.

## Write path (`save_memory`)

Latency per note written, at three corpus sizes. Lower is better.

| Corpus size | p50 | p95 | p99 | max | mean |
|-------------|-----|-----|-----|-----|------|
| 100 notes | 45.9 ms | 57.2 ms | 83.2 ms | 83.2 ms | 47.0 ms |
| 1 000 notes | 75.1 ms | 109.0 ms | 111.8 ms | 114.5 ms | 76.1 ms |
| 10 000 notes | 416.9 ms | 2008.1 ms | 3107.1 ms | 6851.5 ms | 629.5 ms |

**Notes**
- Numbers above are the **core path with LLM fact extraction disabled**. Save latency grows with corpus size because each write performs an incremental FTS5 index insert that gets more expensive as the index grows.
- **With the default config (LLM extraction ON)**, a single `save_memory` call at 100 notes measured **~1.4 s p50** (1 497 ms mean across 100 writes). The Qwen2.5-3B extractor loads once (~10 s first call) and then extracts facts per note. This dominates write latency in the default configuration — budget for it if you rely on automatic fact extraction.
- The `defer_expensive=True` default means embeddings + KG extraction are enqueued to the background worker, so the `save_memory` call itself returns without waiting on the model — but LLM fact extraction (above) is **not** deferred and runs inline.
- Tail latency at 10 000 notes (p99 ≈ 3.1 s, max ≈ 6.9 s) comes from periodic FTS5 checkpoint / write-queue session rollbacks interleaved with the steady insert stream, not from any single operation.

## Search path (`search_memories`)

Latency per query, at three corpus sizes. Lower is better.

| Corpus size | Mode | p50 | p95 | p99 | max | mean |
|-------------|------|-----|-----|-----|-----|------|
| 100 notes | Hybrid (BM25 + vector) | 27.8 ms | 30.6 ms | 30.6 ms | 30.6 ms | 28.4 ms |
| 100 notes | FTS5-only (BM25) | 330.2 ms | 338.5 ms | 338.5 ms | 338.5 ms | 279.2 ms |
| 1 000 notes | Hybrid (BM25 + vector) | 27.6 ms | 31.0 ms | 31.0 ms | 31.0 ms | 28.5 ms |
| 1 000 notes | FTS5-only (BM25) | 336.0 ms | 342.3 ms | 342.3 ms | 342.3 ms | 310.4 ms |
| 10 000 notes | Hybrid (BM25 + vector) | 55.5 ms | 65.3 ms | 65.3 ms | 65.3 ms | 56.2 ms |
| 10 000 notes | FTS5-only (BM25) | 450.0 ms | 1218.4 ms | 1218.4 ms | 1218.4 ms | 599.3 ms |

**Notes**
- **Hybrid (the default `hybrid=True`) is sub-100 ms at all measured sizes and meets the "sub-100 ms search" design goal on Apple Silicon.** This is the latency users actually experience.
- **FTS5-only mode (`hybrid=False`) is ~10× *slower* than hybrid** (330–450 ms vs 28–55 ms). This is unexpected and is captured here as measured; the non-hybrid code path appears to pay a penalty the hybrid path avoids (likely a missing fast-path or a full-scan fallback when vector fusion is disabled). Treat FTS5-only as the *worst-case* search latency, not the typical one.
- **Semantic / vector search could not be measured on this host.** The vector backend requires the `model2vec` package, which is **not installed in this venv** (`Embedding search unavailable. Install model2vec`). The `perf_envelope.py` "semantic_search" row of 0.0 ms is therefore a **false zero** (the search short-circuits to empty when the model is absent) and must not be quoted. On a host with `model2vec` installed, re-run `eval/perf_envelope.py --quick` to populate that number. The hybrid numbers above already include the semantic-fusion branch where the backend is available; on this host it degrades to BM25.
- `deep_rerank=True` (cross-encoder) was **not** measured: it loads `cross-encoder/ms-marco-MiniLM-L-6-v2` (~90 MB) and is known to hang on Apple Silicon MPS, so it is intentionally left out.

## Index operations

Measured by `eval/perf_envelope.py` at a 1 000-note corpus (raw component timings, not the full orchestrator).

| Operation | Time (1K corpus) |
|-----------|------------------|
| FTS5 direct `MATCH` query (raw sqlite3) | 0.7 ms (p50) |
| FTS5 full rebuild (`rebuild_index.py`) | 1 436 ms (p50) |
| Pinned-decay dry-run (SELECT pinned + per-note psi) | 0.7 ms (p50) |
| Contradiction detection — phrase (`--mode=phrase`, 200-note subsample) | 100 ms (p50) |
| Contradiction detection — semantic (`--mode=semantic`, 200-note subsample) | 769 ms (p50) |
| Direct single-row `INSERT` (no frontmatter parse) | 4.1 ms (p50) |

> The contradiction detector is O(n²); the figures above are for a 200-note subsample and are only indicative of the per-pair cost, not the full-corpus cost.

## Worker throughput

> **Not re-measured in this run.** The benchmark scripts in `eval/benchmarks/` measure only save and search *latency*, not background-worker *throughput*. The figures below are representative engineering estimates for the worker (embedding / KG / mixed task rates) and should be re-derived from a worker-level benchmark before being quoted as SLA.

| Scenario | Throughput (estimate) |
|----------|------------------------|
| Embedding tasks only | ~120 tasks/min |
| KG extraction (3 entities/note) | ~40 tasks/min |
| Mixed (50 % embed, 50 % KG) | ~75 tasks/min |

Per-task timeout: 120 s (configurable via `MEMORY_WORKER_TASK_TIMEOUT_S`).

## Running your own benchmarks

The benchmark scripts **exist in the repo** (the old "scripts are not yet included" note is stale). They require the project venv.

```bash
# Save latency across 100 / 1K / 10K corpora
venv/bin/python eval/benchmarks/bench_save.py

# Search latency (FTS5 + hybrid) across 100 / 1K / 10K corpora
venv/bin/python eval/benchmarks/bench_search.py

# Full perf envelope (1K corpus, all component timings)
#   --quick  = 1K only (smoke test, ~20 s)
#   --sizes 1,10000 = custom corpus sizes
MEMORY_USE_USEARCH=0 venv/bin/python eval/perf_envelope.py --quick

# To isolate the core write/search path from the LLM fact extractor and
# drift-enforcement blocks, set:
export MEMORY_USE_USEARCH=0
export MEMORY_LLM_EXTRACTION=0
export PYTEST_CURRENT_TEST=1   # disables config-drift enforcement
```

Results are written to `eval/results/bench-save.json`, `eval/results/bench-search.json`, and `eval/results/perf-envelope.json`.

## Verification

Run the benchmark scripts and compare against the tables above. Expected (on Apple Silicon, core path, extraction off):

- Save p50: ≈ 46 ms @100, ≈ 75 ms @1K, ≈ 420 ms @10K notes.
- Search hybrid p50: ≈ 28 ms @1K, ≈ 55 ms @10K notes (sub-100 ms — meets design goal).
- Search FTS5-only will be materially slower (~330 ms+); this is expected given the current non-hybrid path.

## Known issues found while benchmarking

These were discovered and fixed/flagged during the measurement run:

1. **`bench_search.py` called `search_memories(search_mode=...)`** — that keyword does not exist. The orchestrator uses the boolean `hybrid` flag (`hybrid=True` = hybrid, `hybrid=False` = FTS5-only). The script now maps its `"fts"`/`"hybrid"` modes to `hybrid=(mode == "hybrid")` and passes a `Path` for `db_path` (LSP fix). *Fixed in this change set.*
2. **Config-drift enforcement hard-blocks saves during benchmarks.** Any env-var override that conflicts with `memory.toml` triggers a `DriftEnforcementError` on `save`/`search`. Use `PYTEST_CURRENT_TEST=1` (or run under `pytest`) to disable per-operation enforcement for measurement. This is by design for live processes; it just needs the test bypass for offline benchmarking.
3. **FTS5-only search mode is slower than hybrid** (see *Search path*). Worth a follow-up investigation — the non-hybrid path should not be the slow one.
4. **`perf_envelope.py` "semantic_search" reports 0.0 ms when `model2vec` is absent** instead of erroring or marking the measurement invalid. The 0.0 ms is a false zero and is excluded from the tables above.

## Troubleshooting

### Search latency is much higher than benchmarks

**Cause:** Running the FTS5-only (`hybrid=False`) path (≈330 ms+ in these measurements), or the database has grown well beyond the benchmarked sizes, or the reranker is enabled (adds 30–250 ms).
**Fix:** Use the default hybrid mode. Disable the deep reranker (`MEMORY_RERANKER_DISABLED=1`) and rebuild the FTS5 index if needed. Check vector-index drift with `agentic-memory-integrity`.

### Write latency spikes / saves blocked

**Cause A:** LLM fact extraction is enabled (default) — adds ~1.4 s per note at small corpora (see *Write path*).
**Cause B:** Config-drift enforcement treating a flag override as a source conflict and raising `DriftEnforcementError`.
**Fix A:** Accept the cost, or disable extraction for write-heavy batch loads with `MEMORY_LLM_EXTRACTION=0` (note: you lose automatic fact extraction).
**Fix B:** Ensure `defer_expensive=True` (default) so embedding and KG extraction run asynchronously, and use `PYTEST_CURRENT_TEST=1` for offline benchmarking.

### MPS kernel hangs on Apple Silicon

**Cause:** PyTorch MPS backend incompatibility with the cross-encoder model.
**Fix:** Set `reranker_disabled = true` in `memory.toml` or `MEMORY_RERANKER_DISABLED=1`.
