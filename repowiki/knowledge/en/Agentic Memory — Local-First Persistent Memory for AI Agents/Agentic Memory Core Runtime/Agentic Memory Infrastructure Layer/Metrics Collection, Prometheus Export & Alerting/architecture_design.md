Four sibling modules form the observability surface of the process:
- `infra/metrics.py` owns a module-level `_RuntimeCounters` singleton (`_runtime`) that holds thread-safe in-process counters and a rolling window of latencies; `record_event()` is the public hook called from MCP tools/search/save. `get_stats()` reads historical data from the `memory_audit_log` table via `infra.memory_common.open_db`, while `format_prometheus` / `format_text` render two output modes. The file is also executable (`--prometheus`, `--runtime`, `--reset`).
- `infra/metrics_server.py` is a separate single-process HTTP server (stdlib `http.server.HTTPServer` on port 9464) exposing `/metrics` (Prometheus text format) and `/health`. It re-queries the SQLite DB directly using a single compound SELECT plus a tier GROUP BY, independent of the in-process runtime counters.
- `infra/error_counter.py` provides a global `ErrorCounter` singleton (lazy double-checked via `get_counter()`) that records swallowed exceptions per phase with timestamps and truncated message history, used to make silent failures visible.
- `infra/alert.py` resolves channels from env vars into an `AlertConfig` singleton and dispatches to Slack webhook, SMTP, or Pushover via stdlib `urllib.request`/`smtplib`; each channel failure is logged but does not abort the others.

Dependency direction: all four modules depend only on stdlib + `infra.infrastructure.resolve_active_memory_dir` / `infra.db.open_db` / `infra.memory_common.open_db`; they do not import each other, so the metrics server can run as a detached process alongside the main application.
